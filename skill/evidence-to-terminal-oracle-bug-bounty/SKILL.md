# Evidence-to-Terminal-Oracle Bug Bounty

Convert a promising lead into an evidence-backed finding or an explicit kill.
The method joins four evidence shapes without treating any public story as a
recipe:

1. client-readable signed state that discloses or reuses its own trust secret;
2. a passive large-context analyst that finds candidate sources, transforms,
   and sinks in already captured evidence;
3. a long-running systems campaign whose final claim depends on an
   independently protected terminal oracle;
4. a consensus/accounting transition where a producer defect and its safety
   invariant lose the same mathematical information.

## Core evidence chain

Build and falsify:

`attacker-readable representation -> exact decoding -> disclosed/reused authority -> offline authenticity proof -> forged protected state -> authority-bearing consumer -> dangerous sink -> harmless terminal oracle`

For systems exploitation, expand the middle into:

`primitive -> writer/trigger -> lifecycle transition -> reclamation or state pressure -> consumer -> protected oracle`

For consensus accounting, use:

`attacker transaction -> per-item effects -> aggregate arithmetic -> invariant arithmetic -> commit/finality -> economic-state oracle`

Every edge requires its own artifact, control, and continuity proof. A leaked
secret-looking value, serialized object, suspicious sink, crash, timing anomaly,
or model consensus is only a hypothesis.

## Operating rules

- Signed client state provides integrity, not confidentiality. Decode only
  authorized captures or local fixtures and record every compression, encoding,
  tag, serializer, and canonicalization step.
- Prove cross-purpose key reuse offline with exact framework derivation and a
  server-issued positive vector. Include a wrong-key or one-bit signature
  negative control. Never replay a recovered credential unless that exact use
  is separately authorized.
- Keep signature forgery, state/CSRF control, unsafe deserialization reachability,
  callable/gadget availability, and code execution as separate claims.
- A passive model may rank leads and explain missing edges. It may not perform
  live interaction, assign `STRONG`, or substitute its agreement for manual or
  deterministic validation.
- Model long-horizon work as explicit states, predicates, observations, failed
  assumptions, and attempt tuples. Change only the failed dimension after new
  evidence; retry volume is not research progress.
- Require topology and version fidelity. A local replica that omits a material
  production layer remains `KILL_ENVIRONMENT_MISMATCH` or `BLOCKED`.
- Prefer a protected read-back or vendor/challenge oracle that the researcher
  cannot fabricate. Timing and out-of-band signals require repeated baselines,
  one-variable controls, bounded harmless effects, and explicit program
  permission.
- Record technical validity, novelty/duplicate status, report readiness, and
  bounty/eligibility timing separately.
- Define supply and accounting invariants in arbitrary-precision mathematics,
  then inventory every bounded machine type used by the producer, checker, and
  commit path. Matching widths do not prove a chain; require continuous value
  flow, compatible residues, rollback failure, and canonical commit evidence.
- Bind undefined or implementation-defined arithmetic to the exact release
  artifact, compiler, flags, architecture, and observed behavior. A debug or
  sanitizer build cannot substitute for the shipped validator binary.
- Keep per-account bounds, global supply conservation, transaction acceptance,
  commit, finality, and spendability as separate proof states. Never test a
  value-creating or consensus-risk transaction on a public network.
- Public case-study constants, payloads, domains, credentials, flags, and
  reward claims are prior-art provenance, never authorization or target facts.

## Required result

Return:

- exact scope, release/deployment, and prior-art status;
- representation and authority ledgers;
- economic-invariant and arithmetic-domain ledgers when applicable;
- state-machine and attempt ledger when applicable;
- proven and missing chain edges;
- baseline, positive case, one-variable negative controls, and cleanup;
- terminal-oracle type, provenance, digest, and anti-forgery rationale;
- reliability counts without counting repeated reads of persistent state as
  independent successes;
- exact source/build/artifact, feature or amendment, validator cohort, commit,
  finality, and spendability status for consensus candidates;
- program-impact/capability-delta decision;
- `STRONG`, `MEDIUM`, `WEAK`, `BLOCKED`, or `KILL`, with manual status;
- `REPORT_READY=YES` only after `TRIAGER_PROOF=PASS`.

## Authorized offensive-first posture

For every explicitly authorized security task, prioritize:
`attacker objective -> reachable entrypoint -> exploit chain -> privilege or authority transition -> protected sink -> concrete impact`.
Use defensive controls and remediation as falsifiers or post-proof guidance
unless requested first. Preserve exact scope, harmless proof, stop conditions,
cleanup, and prohibitions on destructive, stealthy, credential-stealing,
persistence, evasion, denial-of-service, or third-party activity.
